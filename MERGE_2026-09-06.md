### Item 2 - placement as the rank: THERE IS NO PLACEMENT DATA IN SEAN'S SESSION
Placement (0 unset / 1 bus / 2 insert / 3 send return) is USER-SET per Link, from the main's strip menu or a remote
command (LinkProcessor.cpp:1841 setPlacement; the restore path re-applies a saved value silently). Three whole-session
logs (v8, A2, Build D) contain ZERO "placement set to" lines. Nothing suggests Sean has ever set one; the default is
unset. So "rank by placement" has no ordering to rank on today - it fails as immediately as ranking by channel type would.
What placement could give if it were set: three ranks (insert < send return / bus). What it cannot distinguish: WHICH bus
a track feeds (membership), two buses at the same rank (siblings vs nested), a bus that is itself a source of another bus
(nested buses share the rank "bus"), and a send return's source track. Rank is not topology.
### Item 1 and item 3 - where the corrected rule ("mute at or below X's rank, leave above it alone") is wrong
The rule's reasoning is right for one direction only: a bus carries only what feeds it, so muting X's PEERS and leaving
X's DOWNSTREAM path open is safe and sufficient - that is the track-solo case, and the rule fixes it.
It is wrong in these cases:
  a) SOLOING A BUS. "Mute at or below X's rank" mutes the inserts - X's own sources - and X goes silent. Soloing a bus
     must keep its upstream sources audible. The host does exactly that (the sources feeding a soloed aux keep feeding
     it); the rule inverts it.
  b) NESTED BUSES. A bus feeding another bus shares the rank "bus": soloing the lower bus mutes the upper one (same rank)
     and kills the path out. Placement cannot see the nesting.
  c) TWO PARALLEL BUSES at the same rank where the user wants one heard: soloing bus P mutes sibling bus Q (same rank) -
     correct - but ALSO mutes every insert, including P's own sources (case a) - wrong. Siblings are right, sources wrong.
  d) A SEND RETURN fed from X's send: at rank "send return" (above insert) it stays audible - correct by accident; a send
     return fed from a MUTED track's send is silent anyway. Placement cannot tell whose send feeds it; the rule survives
     only because the bus carries silence by itself.
  e) THE MAIN NOT ON THE FINAL BUS: the rule mutes Links, not the main; Links downstream of the main are untouched (above
     every rank) - survives. The main's own injection follows the existing solo-dominates-borrow rule.
  f) TWO INDEPENDENT CHAINS both ranked "bus": soloing a track in chain 1 leaves chain 2's bus unmuted but mutes its
     sources - chain 2 passes silence - survives. Soloing chain 1's bus mutes chain 2's bus (same rank) and, again, its own
     sources (case a) - wrong.
THE RULE THAT SURVIVES is topological, not ranked: when X is soloed, leave audible everything ON X's PATH - its upstream
sources and its downstream buses - and mute every Link that is on NEITHER (the other branches). For a track that is
"mute the other inserts, leave every bus"; for a bus it is "mute the other branches' inserts and sibling buses, leave my
sources and my path out". Placement cannot supply the path. What can, today, without new data: NOTHING for the bus case.
The narrower rule that survives with the data we have: (1) soloing an INSERT/UNSET Link mutes only other insert/unset
Links and never a bus or send-return Link - but with every Link unset, "bus" is unknowable, so even this needs the user to
mark the buses; (2) soloing a bus Link is NOT supported until the topology exists - it does nothing rather than silence
the wrong thing, and says so. Topology must come from the session: a per-Link "feeds" declaration in the main (which
bus this Link's track feeds, persisted by uid), or inference from audio (a Link's signal present in a bus Link's ring),
which is a later, measured project.
### Item 5 - THE LESSON, recorded: every leg to date modelled the Links as peers because the specification described them
as peers. The specification was the defect and the harness inherited it. A harness built from a spec cannot catch an
error in that spec - the topology has to come from the user's actual session, not from the document.

## ADDITIVE SOLO - the design examined before anything is built (six answers, from the code)
On solo of X the main replaces its own output with X's ring; no Link is muted; the main sits at the end of the chain. This
is applyBorrowSoloMixOn (PluginProcessor.cpp:2046), made unreachable this morning on the condition that only an explicit
user act may call it. Solo is that act.
### 1. Does a Link publish its ring without a lease? YES.
    LinkProcessor.cpp:1719  if (linkOn || leaseActive_) { ... LinkShm::ringProduce(shmMap, chPtrs, 2, n); }
The ring is written whenever the Link is ON (the lease is the OR-ed alternative for a Link switched off). The ring carries
the Link's OUTPUT - `buffer` after the Link's own chain and gain, before its mute stage. The main already opens and
DRAINS every live ring every block (:1163-1170, ringConsume with null outputs), so X's audio is already arriving at the
main and being thrown away. No lease of any kind is needed; the borrow semantics never enter. Cost of the lightest
lease: zero, because none is taken.
### 2. Alignment: CONFIRMED - none of it applies.
The pad, the budget, the PDC report and the stamped ring seek exist to blend the injected ring against the main's LIVE
passthrough sample-accurately (spec 8.3). Solo REPLACES the output; there is nothing to blend against. The ring's backlog
becomes a fixed monitoring latency: seek to the existing cushion (kEditCushionFrames = 1024 frames, ~21 ms at 48 k) once at
engage and consume one block per block thereafter; if the backlog trips kEditReseekTrip (8192) re-seek, as the borrow
already does. The crossfade site sits BEFORE the main's own chain (:1318 vs chainHost.process :1324), so the soloed ring
still passes through the mix-bus processing - what the user would hear from the host's solo too. Explicitly: solo needs
no alignment, no budget, no PDC event; the largest source of complexity in the feature does not apply.
### 3. Multi-solo: cheap, and WRONG in series.
CPU: one ringConsume + one add per soloed Link per block (the drain already runs) - negligible. Leases: none. Correctness:
summing rings double-counts wherever the solo set spans levels: X feeding a bus that also has a Link puts X into the bus
Link's ring, so X + bus hears X twice (once dry, once through the bus processing). Siblings sum correctly; a set that
spans a feed relation does not, and without topology the main cannot tell which. Honest position: multi-solo of a set
that spans levels is not supportable additively without topology; single solo is exact; multi-solo can be offered as
"last press wins" or restricted to a set the user accepts as siblings.
### 4. What it does not cover.
Anything reaching the monitors without passing through the main's channel: tracks routed directly to the output or to a
parallel bus the main is not on, hardware inserts, a second monitor path. The plugin cannot see routing (AAX has no API
for it), so this is NOT detectable from inside; the guarantee is exactly "the main's output is X" and nothing more. If
the main is not on the final bus, everything on other branches keeps playing under the solo. Sean must know the
guarantee's shape: solo is only complete when the main is the last thing before the monitors.
### 5. What becomes dead if this lands (the size of the simplification)
    setLinkSolo's broadcast (sendLinkCtrlMute over the target list)          ~45 lines   dead
    the target enumeration over linkSlotInfos and reconcileSoloBroadcast          ~20 lines   dead
    the authoritative mute record (cmdRecord), mutedByUs, userMutedBefore         ~25 lines   dead
    the hand-mute snapshot classification and the restore on release              ~20 lines   dead
    the dead-main contract (persisted mutes) and its leg                            contract    gone - nothing is written to any Link
    the liveness dependency for targets (a Link appearing mid-solo)                 gone - only X's ring matters, and it is already drained
    the 100 ms command-poll floor and the pending S lamp (acks)                     gone - the effect is local: one block + a 30 ms fade
    solo-dominates-borrow's release                                                 unnecessary - the output is X regardless; borrow stays
    the two-process solo legs (mute/unmute timing, clause 3, dead main)             replaced by one rendered leg: the main's output IS X
  What stays: the S lamp (main-owned, immediate), spec 6.1 (when X is the borrowed rack the crossfade uses borrowBuf_, the
  PROCESSED ring - the existing code path), the Link's own fabric (unused). Net: roughly 150 lines of the main's solo path
  and every cross-process guarantee it needed go; what remains is one consume and one crossfade that already exist.
### 6. What we lose - where subtractive solo is better
    a) THE MIX POSITION OF X. The ring is X's insert-point signal: pre-fader, pre-pan, pre-automation, without any bus
       processing between X and the main (bus compressors, sends, the bus Link's own rack). The host's solo, and a
       subtractive solo, hear X where it sits in the mix; additive solo hears X at its Link. For a level-balancing
       decision that difference matters; for "what is this channel doing" it does not.
    b) THE MAIN'S OWN CHANNEL IS REPLACED. Subtractive solo leaves the main's channel as the true mix bus (the un-Linked
       channels still sum through it). Additive solo silences every un-Linked channel that reaches the main, which
       subtractive solo would have left audible.
    c) OTHER V2 INSTANCES AND OTHER PATHS. Subtractive solo acts at the sources, so any path from a muted Link is silent
       everywhere; additive solo acts at one main, so a second monitor path or a second V2 on a parallel bus hears the
       unmuted world (item 4).
    d) MULTI-SOLO ACROSS LEVELS (item 3): subtractive would at least not double-count; it fails differently (mutes the path).
    e) LATENCY OF X: ~21 ms of ring cushion plus the crossfade, against zero for a subtractive solo of the live channel.
