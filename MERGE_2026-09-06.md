## CAPTURE AT 45 LINKS (6 Sep 2026, Sean's question): MEASURED
### 1. Payload. What a capture turn sends, measured through the real code (tools/merge_gate_tests/link_levels_payload_test.cpp,
### the editor's own buildLinkLevelsContext over planted live rows with meter frames; MeterEngine::meterDataToJSON)
    the main meter blob (one MeterData, 64 spectrum bins): 660 bytes, does not scale with Links
    the per-Link part = the [LINK LEVELS] injection in the newest message: one text row per live Link
      1 Link  3,530 bytes (3.4 KB is fixed rules text)   16 Links 5,892 bytes   45 Links 10,474 bytes  (~155 bytes per Link)
    the newest turn's other injections (plugin list, chain rules, builtins with schemas, current chain): 61-70 KB,
      measured on live sends (EchoJayHistoryTrim.h / buildChatRequestBody's own record)
    history: capped at 12 messages AND 24,000 bytes, walked newest-first; the newest message is never charged
    TOTAL request body, capture turn:  1 Link ~ 95 KB     16 Links ~ 97 KB     45 Links ~ 102 KB
    The per-Link cost is ~155 bytes; 45 Links add ~7 KB to a ~95 KB request. No cap in buildLinkLevelsContext
    truncated the 45 rows (all 45 present in the measured output).
    Per-channel CAPTURE audio is NOT in the request: each Link's captured WAV is written locally (wavFilePath) for
    review/playback; the turn carries busCount and the rows above.
### 2. Server request limit. The API runs on Vercel (RELEASE.md, the dev transport); Vercel's documented request-body
    limit for serverless functions is 4.5 MB. ~102 KB at 45 Links is ~2% of it. NOT measured against production
    (no synthetic oversized POST was sent to the live API); documented limit quoted. Model context: ~102 KB is
    roughly 25k tokens - the model is the server's choice and its window is not visible from here.
### 3. Timeouts. THE SAME SHAPE AS THE DASHBOARD MINT: streamChat uses a 60 s CONNECT timeout only
    (EchoJayAPI.cpp:1828 "connect phase ONLY - withConnectionTimeout does not bound the read loop"); the read loop
    (:1941) has NO deadline - it ends on EOF, on error, or when the USER cancels (ChatStreamHandle::cancel unblocks
    the read). A server that accepts the request and never answers leaves the turn open with no terminal outcome.
    The non-streaming sendChat -> postJSON -> readEntireStreamAsString has no read timeout either. The classifier
    request (:1663) is the one call with a deadline latch. RECORDED for the residual list; not built tonight.
### THE RULE (degrade and say so) - one violation found
    EchoJayProcessor::startCapture (PluginProcessor.cpp:2859-2862) captures a Link only if
    `activeLinkSlots[i].displayName.isNotEmpty()`: an UNNAMED Link (empty registry name - a Link the main plugin
    lists as "Untitled N") is SILENTLY LEFT OUT of a capture. With provenance, Links carry their track names, so this
    bites only a Link with no track name and no typed name - but when it bites it is exactly the failure the rule
    names: the turn claims busCount from snap.channels while the unnamed Link never entered the channels at all.
    Fix shape (not built tonight): capture every connected slot, name the unnamed ones "Untitled N" the way the
    display list does, and say in the injection when a Link was excluded and why. buildLinkLevelsContext already
    holds the right principle in its own text: "names the shortfall, and a silently capped number is worse".
