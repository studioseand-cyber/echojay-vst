# A2 (U1): the written-out plan card — design (28 Oct 2026)

C1 is settled (`CONTRACT_PLAN_WIRE_2026-10-27.md` plus the four points B took from my review, 11:30),
so this is what A2 builds. Written before the code, because three of its decisions are the kind that
look right and are not.

## 1. The model: `PlanRun`, beside `RunView`, not inside it

`EJAgentRunView.h` already has the pair the card needs — `RunStep` (a row: label, detail, right word,
chips, status) and `RunView` (a run: opening, closing, steps) — with **one pure layout function**,
`layoutRun()`, that the paint pass, the measure pass and the rig's published row all read. That is the
shape to copy, not to extend:

```
struct PlanChannel { juce::String uid, name, role; int order; juce::StringArray caps; };
struct PlanStep    { juce::String id, channelUid, channelName, stage, op;
                     juce::String text, where, plugin, control, unit, howTo;   // detail.*
                     double value; bool forYou, undoWeak; juce::String check, why, status; };
struct PlanRun     { juce::String id, heading, source, kind, scope, mode;
                     std::vector<PlanChannel> channels;
                     std::vector<PlanStep>    steps;
                     juce::StringArray        warnings;
                     std::vector<PlanLeftOut> leftOut; };
```

**Why a second model rather than reusing `RunView`:** a run is what happened, a plan is what is
proposed, and the two differ in the one place that matters — a plan's step has **no result** and a
run's step has no channel section. Folding them would give every `RunStep` a nullable channel and
every `PlanStep` a nullable undo token, which is how one model becomes two behaviours. They meet at
`mode: "agent"`: a plan handed to the agent becomes a run, and the run's steps carry the plan's step
ids (C1 §1: *"becomes the tool_call id when the agent runs it"*), so the two can be read side by side
without either knowing the other's shape.

## 2. The channel resolve, at load, once — the one thing C1 asks of the plugin

C1 §1: a step for the V2's own rack carries `channel: "self"`. In this plugin `"self"` already means
**the channel this run is aimed at** (`resolveChannelArg` maps `""` and `"self"` to `target_`), so a
session-scope step saying `"self"` while a Link is the target would land on the **Link**. B took my
second option: the wire keeps `"self"`, and **the plugin resolves every step's channel to a concrete
rack when the plan loads**, before anything is drawn.

So `PlanRun::fromVar()` resolves `"self"` to the own rack's uid (**the empty string**, which is what
the own rack is everywhere inside this plugin) and keeps the resolved uid in `channelUid`. Nothing
downstream ever sees `"self"`: not the card, not the runner, not `resolveChannelArg`.

**The leg that proves it** is the one §5's sentence is about: a plan whose step says `"self"`, loaded
**while a Link is the working channel**, draws and runs on the own rack. Both directions — and the
control is the same plan with a Link's uid, which must draw and run on that Link however the working
channel is set.

## 3. What the card draws, and what it must not

- **Painted zones, not child components** (`MATCH_SCREEN_CONTRACT` §5, and the reason the Match report
  is painted): the button pools are fixed (`kMaxWavePlayBtns` is 8, the Apply pool is its own), and a
  plan can hold 150 steps. So rows, the per-channel headings, Go, and "Do this one for me" are all
  painted with hit zones, and the only components are the ones that already exist.
- **Every channel's section expanded** (PX §2-§3), in `channels[].order`, with its steps in the order
  C1 guarantees (all of one channel's together; `track`, `group`, `bus`, `mix_bus`).
- **The warnings above the steps, before Go** — at most 8, each at most 200 characters, drawn as sent.
- **`left_out` is drawn, with its reason in plain words, and never in the step list.** A step that
  failed validation is not a step; a card that hides it is a card that silently does less than it was
  asked.
- **`detail.text` is drawn as sent.** It is written by the server from the op, the plugin's map and
  the rules file, and it is a complete instruction. The plugin does not compose a second version of
  it — that is the mistake `pendingClaimText` exists to prevent on the other surface.
- **The tense rule applies here too** (Sean's point 2, 28 Oct): while the plan awaits his approval,
  nothing on it may read as done. `echojay::pendingClaimText` is already the one rule for that, at
  draw time, and the plan card inherits it by construction rather than by a second copy.
- **`undoWeak` rows say so**, in the plugin's own words, because the plugin is the side that knows why:
  two slots holding one plugin name cannot be told apart at undo time (`recordRemoteAddsForUndo`).

## 4. Where it lands in the editor

The plan card is a **chat card**, like the match report and the run row: one entry in the chat with its
own painted body, drawn by the same paint loop and measured by the same pass. So:

- `EJPlanCard.h` — **pure layout**, `layoutPlan (const PlanRun&, int x0, int y0, int width)` returning
  rects and strings exactly as `layoutRun` does, with its own hit zones. No JUCE components, no state.
- `EJPlanRun.h` — the model above plus `fromVar()`, including the channel resolve. Pure, so a guard
  can hold a plan document and assert what the card would draw without an editor at all.
- `PluginEditor.cpp` — the paint call, the press handling, and the one road that posts
  `/api/plan/close` from the plugin's own copy of the plan (C1 §3, and a 404 there is **not** a failed
  run: the plugin closes with what it has).

That split is the same one `EJCompareFigures.h` and `EJMatchReport.h` use, and it is what lets the
rig's `drawn.txt` carry a plan card without a server.

## 5. The legs, before the drawing

In `chat_store_guard` (where the pure-decision legs live), against C1's own fixtures in
`scripts/fixtures/plan-wire/` so the plugin and the server cannot drift:

| leg | what it holds |
|---|---|
| PL0 | `plan-chain-session.json` loads: 4 channels, 6 steps, the `left_out`, the `dependsOn` |
| PL1 | **a `"self"` step resolves to the own rack while a Link is the working channel** (and the control: a Link's uid resolves to that Link whatever the working channel) |
| PL2 | every step's channel is one of `channels[]` after the resolve — a step that names a channel the plan does not carry is dropped, with its reason |
| PL3 | `left_out` never appears in the step list, and its reason is drawn |
| PL4 | a 150-step plan lays out without a component (the pool is untouched) and every row has a hit zone |
| PL5 | `undoWeak` draws its sentence; a plan without it does not |
| PL6 | while the plan awaits approval, no row reads as done (`pendingClaimText`, both directions) |
| PL7 | `draft-nothing-to-plan.json` draws its sentence and no step list at all |
| PL8 | the close body carries one result per step, with `Declined -> skipped` and `Stopped -> not_run` |

## 6. What A2 does NOT do

M3-lite's **runner** (take, run, release, next, channel by channel) is A4's row in the build plan, and
the walk-through is A5. A2 is the card: it draws a drafted plan, it can refuse one it cannot read, and
its Go hands over. Keeping the runner out is what makes A2 gateable on fixtures alone.
