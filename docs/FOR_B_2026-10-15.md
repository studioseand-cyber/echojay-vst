## 3. NEW: settings carried on `add` / `replace` / `build` are now read back

**This is the one with the sharpest edge, and it changes what a result means.** Sean, top priority:

> *"It was added to the Link, but its Attack is still 0.00 dB, while the closing said 'attack pushed up
> +6 dB and sustain pulled down -2 dB'. Last night's fix made SET read values back; settings carried on ADD
> and BUILD are still confirmed by slot count only."*

He picked **MTransient** (Melda, demo). From the Link's own log:

```
EJDial: slot 1 ("MTransient") NO MAP for fp=3decf53d6bc0
        fetch_requested=n in_flight=n fetch_wired=n cached_maps=181 -> noMap
EJApply: slot 1 "MTransient" hadState=Y seeded=Y -> withheld=N edited=N action=LEAVE-UNEDITED
```

**No map, so nothing was dialled.** The settings were never applied at all. The add's read-back counted ONE
SLOT, found one, and said yes — which it was right about. The slot is not the settings, and nothing was
asking about the settings.

### What a `do` result now carries

Every op that carries settings — `add`, `replace`, `build`, per slot, on the open rack and on a Link — is
followed by a value read-back, and the result gains:

```json
"settings_state":      "applied" | "partly_confirmed" | "not_applied" | "not_confirmed",
"settings_confirmed":  true | false,
"settings_asked":      2,
"settings_applied":    "slot 1 attack_db 6.00",
"settings_unapplied":  "slot 1 attack_db is 0.00 (asked 6.00)",
"settings_unreadable": "attack_db, sustain_db"
```

- **`applied`** — every asked value was read back and matches.
- **`not_applied`** — a value was read back and is NOT what was asked. MTransient's Attack at 0.00 dB.
- **`not_confirmed`** — this build cannot read that plugin's values at all: a third party with no map. There
  is no evidence either way, and that is what it says.
- **`partly_confirmed`** — some read back and matched, others could not be read.

**The op itself still succeeds when the slot landed**, because it did — failing it would make the model add
the plugin a second time, which is worse. The landed line says which state it is in and, when nothing was
confirmed, tells the model in as many words not to name a figure it was not given.

### WHAT I NEED FROM YOU (3)

**The closing text must be built only from what the read-back confirmed.** This is the same rule as the
`set` read-back from yesterday, now reaching three more ops, and it is the one Sean has raised three rounds
running. Concretely:

- `settings_state != "applied"` → **do not state any parameter value in the closing text.** Say the plugin

- `settings_state == "not_applied"` → say so plainly, and do not offer the asked figures as though they

- Please do not paper over `not_confirmed` with "should now be". Sean's words, three rounds ago: *"a set must

## 4. `check(gr)` now returns the LISTEN WINDOW, and the field names changed

Sean's checks 2 and 3. His meter showed about 5 dB on the loud parts and the agent reported **0.1 dB**, then
**2.1 dB**. The cause, from the code rather than a guess:

`EedDynamicsCore::gainReductionDb()` returns `grDb_` — one float, overwritten every audio block, the
editor's meter tap. `ChainHost::slotPicture` read it **at the moment it was asked**, and `check(gr)` asked
once, right after the listen window ended — i.e. in the release tail. It was the instantaneous reduction at
one arbitrary instant, and the instant was systematically the worst one available.

The device now accumulates over the listen window, **on the audio thread where every block is seen** (a peak
hold and a histogram for the median), **gated on audio actually being present**, and the window is reset when
a listen begins. `check(gr)` returns:

```json
"grPeakDb":       5.1,          // the deepest reduction in the window
"grTypicalDb":    2.8,          // the MEDIAN of the blocks with audio ("typical")
"grNowDb":        0.4,          // this instant only - NOT the figure to quote
"grWindowFrames": 412800,
"measured":       "over the whole listen window, only while audio was playing",
"note":           "grPeakDb is the deepest ... grNowDb is this instant only and is NOT the figure to quote."
```

And when nothing has been measured — no audio through that slot since the window began — there is **no peak
and no typical at all**, only `grNowDb` and a `measured` line saying so. **That is the absence of a reading,
not 0 dB of reduction**, and it must not be reported as "no compression".

### WHAT I NEED FROM YOU (4)

- **Quote `grPeakDb` and `grTypicalDb`, named as peak and typical.** Sean asked for both, in those terms.
- **Never quote `grNowDb`** as what the compressor is doing.
- **When there is no peak/typical, ask for a listen with audio playing** rather than reporting a figure.
- `look(rack)` carries `grPeakDb`/`grTypicalDb` per slot alongside `grDb` for the same reason, so the two
  reads cannot disagree.

## 5. A refused change now carries the rack's OWN reason

Also Sean's check 5. The add came back `"the rack refused it (partial)"` **twice**, and Details only repeated
that sentence. The Link had written the real line into its ack's `perPluginResults`, and
`awaitChainAck` only ever read `status` and `reason` — and a **build ack sets no `reason`**. So "(partial)",
a count, was the whole of what the V2, the model and the user ever learned.

Now: the troubled per-plugin lines come FIRST in the sentence (a count is not a reason), and the failure is
raised with the model getting a separate **technical** account — the ack's status, every per-plugin line and
the per-plugin detail. On the plugin side that is also what the line's Details disclosure shows, so it can no
longer repeat the summary: the two are different strings by construction, and where there is genuinely
nothing technical, no Details control appears at all.

**Nothing needed from you**, except: `errorMessage` on a `not_applied` is now the technical account and
`userMessage` is the plain sentence. If you were reading `errorMessage` as the user-facing line anywhere,
read `userMessage` instead.
