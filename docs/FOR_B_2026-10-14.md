Implemented. The shape, for your tool schema:

```json
{ "tool": "do", "args": { "op": "undo" } }
```

**No arguments, and no `channel`.** The history is plugin-wide — one stack carrying local and remote edits in
the order they happened — and each entry already knows the target it belongs to. Asking which channel to undo
on would invite an undo aimed at a rack whose step is not the one on top, so the op does not take one.

What comes back:

| outcome | shape | when |
|---|---|---|
| ok | `{undone:true, op:"undo", label:"<what was undone>", depthBefore:N, depthAfter:N-1}` | the step was reversed |
| `not_applied` | `"there was nothing to undo"` | the history is empty |
| `not_applied` | `"the undo history did not move (still N steps deep)"` | it claimed a step and nothing happened — the read-back refusing to call it a success |
| `not_applied` | `"skipped: that Link is no longer present"` (the history's own words) | the step came off the stack but its target had gone. **Never applied to a different target** |
| `not_permitted` | Agent mode is off | an undo is a change |

`label` is the history's own label for the step — *"remove EchoJay EQ"*, *"Link trim Lead Vocal"*, *"rename to
Drums"* — so a reply can name what it undid instead of describing what it assumed. **Please report it from
`label` rather than from the plan**: the whole of row C10 was the model telling Sean it had undone the pre-gain
when the top of the stack was a slot removal.
