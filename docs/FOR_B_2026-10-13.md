# For B — the three things the plugin changed on 13 Oct 2026 that the tool schema has to match

From Sean's in-host round on `ship_2026-10-12b`. Each of these is live in the plugin now; the server side is
B's. Names are given exactly as the plugin reads them, with the alternates it also accepts and why.

---

## 1. `look(what: "inventory")` — a name filter and paging (Sean's item 9)

**The problem.** "What compressors do I have" returned Acme, Abbey Road… — the alphabetical first slice of
1,598 plugins. The 8 KB result rule trimmed the `names` array and set `truncated: true`, and `count` did report
the full 1,598 - so the result was honest about being a slice. What was missing was any way to act on that:
no filter, no offset, so the agent could see it had been cut off and had no way to ask for the rest.

**Request parameters** (all optional):

| name | type | default | meaning |
|---|---|---|---|
| `match` | string | — | every space-separated token must appear in the plugin name, case-insensitive. `"fab pro"` matches "FabFilter Pro-C 2" and "FabFilter Pro-Q 3". |
| `offset` | int | `0` | index into the matched list |
| `limit` | int | `60` | page size, capped at `200` |

`name` and `q` are also accepted as spellings of `match`. That is deliberate and not an invitation to use
them: a model that has not read the schema reaches for those two, and silently ignoring a filter it believed it
sent is the exact failure this item is.

**Response fields:**

| field | meaning |
|---|---|
| `total` | how many plugins MATCHED, before any trimming — the number that tells the agent whether it has covered the list |
| `offset`, `limit` | echoed back, after clamping |
| `returned` | how many are in `names` |
| `hasMore` | `true` while `offset + returned < total` |
| `match` | echoed when one was sent |
| `names` | the page |
| `count` | **unchanged in meaning: the WHOLE list (== `total`)** - before paging this field was set before the 8 KB trim, so it has always been "how many are installed", with `truncated` saying the names were a slice. Reading `count` to answer "how many plugins do I have" keeps working. Use `returned` for the page length. |
| `truncated` | unchanged in meaning: `true` when `names` is not all of `total` (so it is set whenever `hasMore` is) |

`total` and `hasMore` survive the 8 KB trim, which is the point — the agent can always tell there is more.

A filter matching nothing is a **success** with `total: 0`, not a failure. "You have no de-essers" is an
answer the agent can act on; a failure sends it round again on the same question.

## 2. `do(op: "set_rack_out")` — the rack's OUT gain (Sean's item 10)

**The problem.** Sean asked to turn the vocal rack output down 2 dB and the server dialled the EchoJay EQ's
`output_db` — a plugin's output *inside* the rack, not the rack's. The server had no choice: there was no op
that meant "the rack's OUT", so the nearest thing with the word "output" in it won.

Route **"rack output" / "rack level" / "rack volume" / "turn the rack down"** to this op.

| name | type | meaning |
|---|---|---|
| `db` | number | the new gain, ABSOLUTE |
| `delta` | number | a CHANGE in dB — this is what "down 2 dB" means, so prefer it |
| `absolute` | bool | optional; overrides the default. Absent: `db` means absolute, `delta` means relative. |
| `channel` | string | optional, as every mutating op — and ask-first applies to it exactly as it does to the others |
| `confirm` | bool | required for another channel |

One of `db` or `delta` is required. `rack_out` and `set_rack_output` are accepted as aliases of the op name.

**What it moves, so the server can describe it truthfully:** the gain the levelling loop's `rack_out` stage
writes — the V2's own bus gain on this instance, the Link's mixer-strip GAIN on a Link. An agent's change and
a levelling landing therefore move the *same* control, which is what lets one caption describe either.
Clamped to ±24 dB. It is NOT a chain-channel `edit` op and must not be sent as one.

An unknown op's refusal now names the whole vocabulary, so a wrong guess gets a list rather than another
guess: `build, add, remove, replace, move, set, set_wet, set_io, set_master_wet, set_pre_gain, set_rack_out,
bypass, set_level, open_editor`.

## 3. GR and the analyser on a Link — the exact wording (Sean's item 8)

**The problem.** Every measurement read used the rack the window has OPEN, with a slot number from a plan
meant for a different rack. So a GR read aimed at another track answered `slot 2 is not on the rack (1..0)` —
a true statement about the wrong rack, and the sentence Sean's agent retried for eighteen rounds, because it
reads like a mistake worth correcting.

`check(what: "gr" | "true_peak" | "spectrum")` with a `channel` that resolves to a Link, or on a session that
is addressing a Link, now returns:

```
code:    "not_available_on_link"
message: "<What> cannot be read from a Link yet - only from the rack this EchoJay window has open.
          This will not work on a retry."
result:  { "retryable": false,
           "hint": "do not plan a measurement on another track's Link: either work from what look(rack)
                    reports, or ask the user to open that track's own EchoJay window and measure there" }
```

`<What>` is `Gain reduction`, `A true-peak reading`, or `The analyser's spectrum`.

**Teach the agent not to plan it.** `retryable: false` and the hint matter as much as the sentence. The own
rack is unaffected — the refusal is about Links, not about measuring.

This is a **temporary** limit with a known end: queue item 0a replaces the transport (`LinkMeterFrame` is 128
bytes, its size IS the mapping stride, and the pad is spent to the last byte, so remote GR needs a new
versioned region, not a new field). When that lands, this refusal goes.

## Also worth knowing, though it needs nothing from B

* **Target resolution now accepts a labelled uid.** The agent sent `channel: "uid bb411b8240"` and the
  registry holds `bb411b8240`, so every cross-track action failed. A leading `uid` / `id` / `track` /
  `channel` / `link` followed by a separator is stripped, and the raw string is still tried first. Sending the
  bare uid remains correct and is still the best thing to send.
* **A `do` is not reported as applied until a read-back confirms it.** Success used to mean "the command file
  was written". For `build`, `add` and `replace` the executor now re-reads the target rack and refuses if the
  slots are not there, with the figures in the sentence. A server that trusted `applied: true` was being told
  something the plugin did not know.
* **Pressing Apply on a plan line now counts as `confirm: true`** for that line's channel, and the plan line
  names the track. The server does not need to send `confirm` on an ask-first line.
