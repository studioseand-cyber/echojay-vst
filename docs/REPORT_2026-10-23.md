## 1. Your faults, each at its cause

**Test 0 (08:10), the plan shown twice.** Mine, and on a surface the 22 Oct fix could not see. B's
`0d69565` does send the plan once (its own contract of 22 Oct), and it is still sent twice in two

swallowed the model's words would be worse than one that said them twice.

**Test 0 (08:10), "Got it, you can stop" on a build goal.** The rule was *"is a dial pending right
now"*, which at the first listen is always no — nothing is on the rack yet, so there is nothing to be
dialling. A decision about the future taken from the present.

*Fix:* the run says he can stop only when it can honestly promise nothing else will need playback —
which is when it has shown its **closing** (B's own `tc_check` marker). Before that the line is "Got
it." and nothing more. No prose is read from the goal; "is this a build goal" by keyword would be a
proxy. The **button** asks the same function, so the line and the button cannot disagree.

**Test 2 (08:28), runs stall on two Links.** Two different things, and your own hypothesis was right
about one of them:

  **08:29:57**, all while you were elsewhere. What stalled was the **card**.
- **The card stopped being written at your first switch.** `EJAgentHome` found the run's row by

  2 of 18 Oct, which is right). From the first switch the write fell through silently: the Vocal card
  froze on "Thinking…" with no steps while its run was alive. **This is also B's note 1** — the Kick

- **And the Vocal run really was stopped** — by the Kick run starting. One `EJAgentClient` per
  instance, so a second run supersedes the first. That is B's one-run rule, and what was wrong is
  that it happened **in silence**. See B2 below.

*Fix:* the home holds its own row address (the run's chat and entry, taken when the row is minted)
and writes through the **store**, which is the authority. No list and no window decides whether a run
is recorded.

**Test 4 (08:40), the Tube-Tech CL 1B "had not reported them yet".** It waited for **nothing at all**:
the plugin loaded and the step concluded in the same second (08:40:20), and the "re-reading in 800 ms

been read and was *wrong*; a plugin that has reported nothing produces neither a miss nor an
unreadable, so the one case that most needed another look got none.

*Fix:* "asked for something, and nothing has come back yet" joins the two existing reasons. Same

**Test 4 (08:43), the dial's result as a loose message.** Ours, literally: `calibTickAndPost` posted

*Fix:* when the run owns that dial (its own keep-playing list decides, not the prose), the line goes
**onto the dial's step**, which now **finishes and shows its result** instead of vanishing. A

1. **The run was stopped by a Stop PRESS.** `EJAgentRow: press kind=7 step=-` at 08:44:56 — kind 7 is

**And two the RIG found, after Logic was closed - both in the live view I had just written.** Neither
is one of yours; both are mine, and the rig caught them on its first pass over the new feature:

1. **Leaving a Link's rack did not stop the live view**, so a Link kept streaming audio for a picture

## 2. B's four additions

1. **Why the Kick plan card was never drawn** — the same cause as test 2 above, fixed there.
2. **Never supersede a live run silently.** A message typed in another chat now asks first: *"This
   will stop the run on `<channel>`. Start anyway?"* with **Start anyway / Cancel**. Your text rides
   on the chips, so Start sends it and Cancel puts it back in the box — neither answer loses it. The
   channel is named from the **run's own chat**, not the one on screen.
3. **`plugins_unreadable` in the start context.** This machine now remembers a plugin whose values do
   not read back (noted the first time a read-back concludes it, in B's `{name, why}` shape) and
   sends the list on every start, so the first build with such a plugin stops failing once per user.
   **It clears itself** the moment a read-back succeeds — the usual cause is a parameter map that had
   not arrived yet, and a mark that outlived its reason would hold a readable plugin back for ever.
4. **The dial's sides and words.** `controls` is read and **every side moves together** (your Shadow
   Hills finding is the same family); B's `say` sentences are used for the done line, filled with the
   measured `{gr}` and the `{end}` word; `ask: false` means **no question after a dial**.

**And B's question back, answered: the dial did not turn the wrong way — it never turned at all.**
`actuator: "amount"` is explicitly **hold-only** in this build (`configFromBlock`: *"HOLDING and
running the section 7 check, not stepping it — the amount actuator is not implemented yet"*), because
until B's new block there was no `sense` on the wire and guessing a direction was worse than not
moving. So the 0.2 dB was what the add alone achieved, and "+0.0 dB" is a **read-back** of the
control, reported in dB although an amount control is not in dB. Two consequences, both owed and
listed in §5: implementing the amount actuator's stepping (B's `sense` now makes it possible), and
not printing "dB" after a value that is not in dB.

## 6.1 The two crashes, and why the live view is off

Both crash reports say the same thing, with a different plugin each time:

```
_platform_memmove  <-  juce::AudioUnitPluginInstanceHeadless::renderGetInputCallback   (ours)
                   <-  AUInputElement::PullInput   (WaveShell1-AU, 16:33)
                   <-  (UnFairchild, 16:41)
                   <-  EchoJayProcessor::processBlock                                  (ours, render thread)
SIGSEGV, KERN_INVALID_ADDRESS at 0x0, AUHostingServiceXPC
```

**Ours, in our own input callback, on the audio thread, both times.** The live view's copy was handed
a two-channel scratch buffer whatever the plugin was; both of his plugins pull more than two
channels, so JUCE copied from a null pointer. It can only happen through the live view: no other road
hosts a copy from `processBlock`.

*Fixed at the cause, three parts:* the copy is asked for a plain 2-in/2-out with every other bus
disabled; the scratch buffer is then sized to whatever the copy **ended up** with (a plugin may
refuse the layout, which is its right); and every channel past the stereo pair is fed silence rather
than leftovers. Guarded by the arithmetic the null came from (`chat_store_guard` SH8/SH8b: a copy
that reports four channels is handed four, and nothing reads past the end).

**And it is still switched off.** The guard holds the arithmetic and the rig will hold the road, but
neither can load a PACE or iLok plugin - the standing rule on this machine - so the two plugins that
actually crashed cannot be tested here by anything except him. A feature that took his session down
twice in ten minutes does not go back in front of him on the strength of a guard that cannot load it.
One switch (`echojay::kShadowViewEnabled` in `Source/EJShadowView.h`), read in one place, so it comes
back as one line when the rig has proven the road. With it off, a Link slot shows his old line again:
*"The live view of this plugin is coming soon"*, with the settings list beside it as before.

## 6.2 The live view's missing audio - found, fixed, and in the build anyway

Worth having even with the view off, because the same tap feeds it: the picture arrived and nothing
moved because **the tap was pointed at a slot nothing was pushing**. The slot's index was baked into
its pre-trim node when the node was built, and the node is built once per slot; `slots_` is a vector,
so an insert or an erase shifts the elements - and their nodes - leaving a node that still says "I am
slot 0" sitting at slot 1. Two nodes then answer to 0, nobody answers to 1, and a tap aimed at slot 1
is fed by nothing at all. His rack had plugins added through the session.

*Fix:* the index is an atomic the host sets on **every** rebuild, from the slot's address in the
vector - the one place that knows it. This is also the zero-frame reading the rig's B9 row got on both
roads this morning, so it was two reports of one bug.

## 6.4 The dial on playback: why it never ran, on Main and on a Link

Two different causes, both named by his own log.

**On Main (16:26) the dial was refused before it started:**

```
EJThreshold: NOT STARTED - this chain's role is bus ... on a bus the last stage sets the level
EJThreshold: 0 of 1 hold(s) actually started
```

The 29 Sep rule is *"on a bus, nothing writes IN or OUT"*, and it was made for a real fault: a hold
wrote +10.5 dB to a bus slot's OUT and distorted the chain. But it refused **every** dial on a bus,
including one that never touches the slot's staging - and the loop itself already says so, in its own
comment: `preDb = (actuator == Drive) ? startDb : 0`, *"a named control leaves the staging alone"*.

*Fix:* the refusal follows the reason instead of the target. On a bus a **drive** dial is still
refused; a dial that writes the plugin's own named control runs. One rule, one reason, and nothing
that could bring the +10.5 dB write back.

**On a Link (16:40) the dial ran and never wrote.** Every window for eighty seconds:

```
EJThreshold: "UnFairchild" window 13..27  gr=-0.2  level 0.5 dB  crest -0.2 dB  band 0.5-1.5
             mode=listen  state=held-disagree
```

The 3 Oct two-sensor rule is right - nothing moves on one sensor's word without a profile - and it had
**no ending**. A 0.7 dB disagreement on a plugin that is barely compressing will never resolve, so the
dial, the card and the whole run waited for as long as he cared to play. That is the fifth unbounded
wait in that file's history, and its own 8 Oct rule covers it: *"a loop that reads a sensor needs a
deadline, a staleness test on the sensor, and a sentence for each way it can end."*

*Fix:* eight windows (about 24 s) of disagreement and the hold **ends and says what it measured** -
*"<plugin> only reaches 0.5 dB of gain reduction here, and its two meters disagree about it... I have
left it where it is rather than dial on a reading I cannot trust."* A disagreement during one quiet
phrase is ordinary and resets the count; eighty seconds of it is not a phrase, and he should never be
the thing that times out.

**What is NOT in this build, from his test-3 ruling:** *"each dial is its own step right after its
add"* and *"the closing and How's it sounding? appear only once every dial has landed"*. The dial's
step and its result already draw from the run's own keep-playing list and its results (his 08:43
ruling, this morning's build), so with the dial now actually starting they should appear - but the
ordering (the step beside its add) and **holding the closing back until every dial has landed** are
not implemented, and B is writing the server half. That is the next round's, against B's contract
note, and it is the one thing to expect to still look wrong tonight.
