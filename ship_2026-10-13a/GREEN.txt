THE ELEVEN
=====================================================================
1. LINK TARGET RESOLUTION.  Three faults, not one.
   (a) Nothing normalised the channel argument, so `channel: "uid bb411b8240"` - the spelling a model most
       naturally produces after reading "uid bb411b8240" out of the start context - was the one spelling that
       could not resolve. normaliseChannelArg strips a leading uid/id/track/channel/link label, but only with
       a separator after it, so a track really called "linkwood texture" is not stripped.
   (b) "sent" was being reported as "applied". The apply sink returned cb(seq >= 0, ...) and seq is the return
       of a FILE WRITE. That is why the Kick build was reported as landed with nothing on the Kick, and all 18
       of those rounds were downstream of that one false sentence. There is now a bounded ack wait, and the
       executor RE-READS the target rack and refuses with both figures if the slots are not there.
   (c) For the V2's own rack (empty uid) writeChainEditCommand refuses outright, so every agent `do` on the
       open rack had always returned -1. The own rack now applies in-process through ChainHost.
2. ONE OK, NOT TWO.  A plan step names its target track ("on 88_7even Kick_2_01"), and pressing Apply records
   confirm:true for that channel, so the executor does not ask again. A DECLINED line records no confirmation.
3. TOOL ERRORS ARE NOT USER TEXT.  ToolOutcome carries two audiences: userMessage (one plain sentence, no uid,
   no instruction) and errorMessage (the model's detail). A failed row gets a "Details" toggle. Agent replies
   render **bold**, *italic*, _italic_ and `code` through the new EJChatMarkdown.h.
4. A TURN SURVIVES CLOSING THE WINDOW.  The CHAT half is done: the editor hands its live stream to the
   processor instead of cancelling it, the parked chat id makes the keep-rule survive a reopen, and the reply
   is shown or saved. The AGENT half is NOT done and is deferred as queue item 0b, honestly: an agent turn is
   rounds of tool calls run against the EDITOR's executor, so parking its socket would leave a session making
   decisions with nothing to act on. That is item 0's move. Until then the run stops cleanly and says so.
5. REOPEN RETURNS TO THE LINK YOU WERE ON.  lastWorkingUid is persisted (additive state key) and restored on
   reopen, gated on the Link still being live.
6. AGENT CHIP TAKES EFFECT IMMEDIATELY.  The cause was CONSTRUCTION, not liveness: the executor, client and
   panel were built inside `if (agentModeOn())`, so a live gate sat in front of null pointers. Construction is
   now unconditional and the switch is behaviour only. The chip and the Settings switch follow each other.
7. INPUT BOX CLEARS ON SEND.  chatInput.clear() at the top of sendChatMessage - both modes.
8. GR ON A LINK, UNTIL 0a.  A GR/analyser read aimed at another track's Link returns not_available_on_link
   with retryable:false - never "slot not on rack". Exact wording in docs/FOR_B_2026-10-13.md.
9. INVENTORY.  look(inventory) takes match / offset / limit and returns total / offset / limit / returned /
   hasMore / match / names, with `count` and `truncated` keeping their old meanings. Names for B in
   docs/FOR_B_2026-10-13.md.
10. RACK OUT.  A set_rack_out op (db / delta / absolute / channel / confirm) goes to the rack-out sink and

THE RED  (gate7, and why it mattered)
=====================================================================
GATE7 went RED with 1 of 76: agent_executor_read_guard, leg G7a, which asserts that a 400-plugin inventory
comes back under 8 KB with truncated:true and "count still 400".

My item 9 paging had redefined `count` as the length of the PAGE. The old inventoryVar set count = names.size()
BEFORE fitUnder8K halved the array, so `count` has always meant HOW MANY ARE INSTALLED, with `truncated`
saying the names were only a slice. look(list_tracks) uses `count` the same way. Worse, the comment I had
written next to the change asserted the opposite - "kept meaning what it has always meant ... the length of
`names`" - a compatibility claim I never checked, in the one place where a wrong claim is most reassuring. The
same claim was in docs/FOR_B_2026-10-13.md twice.

Had it shipped, B's server reading `count` to answer "how many plugins do I have" would have begun saying 60
instead of 1,598, with no error anywhere.

Fixed three ways:
  - `count` is the total again; `returned` is the only field that means the page length; `truncated` is set
    whenever hasMore is.
  - returned / hasMore / truncated are derived AFTER the 8 KB trim, from the array that actually survived it -
    a value computed before the trim would be a lie about the very field the agent uses to decide whether to
    ask for the next page.
  - FOUR new legs in agent_round13_guard assert the compatibility fact, so the two guards cannot drift apart.
    Red direction proven: with count set back to the page length, G7a fails exactly as the gate saw it and two
    of the new legs go red ("[60]", truncated missing). Source restored byte-identical.

THE LESSON, written down because it is the third of its kind this week: a comment that reassures is not a
check. "Unchanged in meaning" was a claim about code I had not read. Two minutes of `git show HEAD:` would
have settled it, and an existing guard had to do it instead.
