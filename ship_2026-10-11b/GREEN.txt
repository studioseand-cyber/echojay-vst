================================================================================================
THE ONE FAULT
================================================================================================

Three complaints in ship_2026-10-11a were one bug, and the kernel named it:

    AUHostingServiceXPC_arrow[2341] (Metal) failed to open metal library with error: Too many open files

EMFILE in the AU hosting process that runs EchoJay V2 and every EchoJay Link. Once that process cannot open a
file, nothing in it can:

  * a third-party AU cannot open its bundle -> Logic reports -10875 for EVERY one of them, including plain
    inserts, because they share that process;
  * a Link cannot write its rack sidecar -> the V2 says "has not published its rack yet" about Links that are
    working perfectly;
  * a chain build stalls on the first bundle it tries to load -> Logic freezes.

Ten minutes from a clean boot to all three. It then crash-looped (48 crashes in one minute, "couldn't find the
crashing image"), which is why no crash report was ever written and why two earlier diagnoses found nothing.

THE LEAK was mine, from 11 October's stage-3 value ring. openRingForDrain had two faults that compounded:

  * it opened O_RDWR|O_CREAT and deliberately did not initialise - correct in itself, that is the producer's
    job and doing it here races the producer - so for any rack the V2 had never addressed it CREATED a zeroed
    file that can never pass ringUsable(). 361 of those were on disk, every one with magic 00000000;
  * it returned nullptr on the unusable path with the file still OPEN and still MAPPED, because
    openFileMapped does both before anyone can test what it mapped. Its caller records the descriptor only on
    success, so every failure dropped a descriptor and a 16 KB mapping on the floor.

And ringTick retried whenever cmdRing_ was null, in a function that runs at 30 Hz. The comment above it read
"this is attempted quietly and once". It was thirty attempts a second, for the life of the session, per Link.
Not one EJRing line was ever logged, because the failure path said nothing at all.

TWO WRONG READINGS DISCARDED on the way, recorded so nobody repeats them:
  * the V2's "borrow budget WANTED ON" log line is still in this build and proves NOTHING about which binary
    is loaded - I nearly called a stale install on it;
  * kern.num_vnodes == kern.maxvnodes is the NORMAL full vnode cache on macOS, not exhaustion. The kernel had
    no complaint about it.
What settled it was the loaded-image UUIDs in the 14:38 crash report and that Metal line.

THE FIX, three parts
  1. openFileMapped takes createIfMissing (default true, so every existing caller is unchanged) and the ring's
     consumer passes false. Absence means "no ring yet", which is correct and common. A caller that refuses to
     create also refuses to ftruncate, or it would be creating by the back door.
  2. openRingForDrain releases the mapping AND the descriptor on every path that does not hand them to the
     caller, and reports errno 0 - a ring not yet laid down is not an error.
  3. The retry stays, bounded to ~1 Hz. NOT "try once and give up", which is what the V2's producer correctly
     does: a ring legitimately appears when the V2 first addresses that rack, which can be minutes after the
     Link started. The failure now says so once per 30 s WITH THE ATTEMPT COUNT, because the difference
     between "no ring yet" and a leak is exactly that number.

================================================================================================
THE GUARD, PROVEN BOTH DIRECTIONS
================================================================================================

ring_leak_guard (new, gated, LINKSIDE), on the real LinkProcessor, 600 ticks = 20 s of a 30 Hz timer:

                      descriptors        mapped regions     open attempts
  before the fix      604 -> 1204        679 -> 1279        601 in 600 ticks
  after               3 -> 3             76 -> 76           1 in 600 ticks

Legs: an absent ring is never CREATED; descriptors and mapped regions flat across 600 ticks against an
unusable ring (a tolerance of 8, not equality - a process opens things for its own reasons, and a leg that
demands equality fails on an unrelated log rotation); the retry is BOUNDED; and a ring laid down LATER is
still adopted, which is the leg that stops a future tidy-up turning a bounded retry into no retry at all.

It reads the descriptor count from proc_pidinfo and walks its own vm regions, so neither number is a count of
lines of something that could be throttled or truncated.

WHY NOTHING CAUGHT THIS BEFORE: the existing ring legs assert that a frame written is a frame applied. None of
them asked what the MAPPING cost, and none ran for the thousands of ticks a 30 Hz leak needs to matter.
